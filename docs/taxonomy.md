# 分类体系

分类定义在 [`data/categories.yml`](../data/categories.yml)，是唯一的真值源。改名称、顺序只改那个文件，跑 `npm run build` 就会同步到 README 和 `docs/list/`。

---

## 为什么按业务环节分，而不是按技术栈

大多数 Awesome 列表按语言（Python 库 / JS 库）或技术栈（前端 / 后端）分类。这个仓库不这么做，因为**读者不是按技术栈找东西的**。

一个投标经理关心的是「我要把这 300 页 PDF 里的评分表抽出来」，不是「我要找一个 Python 库」。所以分类轴是**招投标与工程建设的实际流程环节**：

```
拿到需求 → 找项目 → 读招标文件 → 做标书 → 报价算量 → 合规自检 → 递交 → 中标后管项目
            ↑公告数据    ↑文件解析    ↑标书制作   ↑造价算量   ↑合规审查   ↑签章加密
```

语言、许可、类型这些维度不做成分类，而是作为**筛选字段**（`language` / `license` / `kind`），放在每行的「信息」列和 `dist/index.json` 里。

## 现有分类与归属判定

| 分类 | 收什么 | 典型的「要不要放这里」问题 |
| --- | --- | --- |
| `announce-data` 招标公告与交易数据 | 抓取、解析公告、开放数据接口 | 爬虫框架放这里；通用 HTTP 库不放 |
| `doc-parse` 招标文件解析与文档理解 | PDF/Word/OFD 抽取、OCR、版面与条款结构化 | PDF 渲染放这里；PDF 页面合成放 `office-toolkit` |
| `bid-doc` 标书制作与文档自动化 | Word 模板、批量生成、排版、转 PDF | 生成标书放这里；通用 docx 读写也放这里 |
| `cost-quantity` 造价算量与清单计价 | 工程量计算、清单计价、钢筋翻样 | 通用电子表格放 `office-toolkit` |
| `bim-cad` BIM / CAD 与图纸 | IFC 解析、模型查看、DXF/DWG、几何内核 | — |
| `compliance` 合规审查与围串标识别 | 雷同检测、资质核验、条款审查、相似度 | 中文分词放这里（服务于条款分析） |
| `esign-crypto` 电子签章与国密 | CA、SM2/3/4、OFD 签章、加解密 | 通用加密库（OpenSSL）不放，除非国密专用 |
| `project-mgmt` 项目管理与协同 | 进度计划、甘特图、任务协同、文档协同 | 中标后的履约管理放这里 |
| `data-ai` 数据、AI 与检索 | LLM 框架、RAG、向量检索、数据可视化 | 通用 AI 框架放这里，但要写清行业用法 |
| `geo-space` GIS 与空间数据 | 地图引擎、坐标、选址、地形 | — |
| `office-toolkit` 通用办公与文档工具 | PDF 处理、OCR、Excel、批量文件操作 | 投标日常高频的通用工具 |
| `learning` 标准、数据集与学习资源 | 标准规范、数据集、教程、社区 | 不是软件但有长期参考价值的东西 |

### 一条只归一个分类

不做多分类。理由很实际：

1. 多分类会导致统计重复（总数 45，各分类加起来 60），读者一看就不可信。
2. 搜索去重、随机推荐、"本分类还有 X 条"这些逻辑全要特殊处理。
3. 更重要的是：**归属本身就是信息**。「这个东西在流程的哪一步用」比「它同时属于三个技术领域」有用。

### 判不准时的决策树

```
这工具是给谁用的？
├─ 写代码的人调用它 → 看它处理什么
│   ├─ PDF/Word/图片里的信息 → doc-parse
│   ├─ 三维模型/图纸 → bim-cad
│   └─ 其它通用能力 → office-toolkit 或按业务环节
└─ 不写代码的人直接打开用 → 看它在流程哪一步
    ├─ 找项目 → announce-data
    ├─ 写标书 → bid-doc
    ├─ 算钱 → cost-quantity
    ├─ 查合规 → compliance
    └─ 中标后管项目 → project-mgmt
```

还是判不准？选**读者最可能去那个分类里找它**的那个，然后在 `notes` 里写一句「也可用于 XXX」。这比纠结分类学重要。

## 新增分类

分类不是越多越好。**空分类会让整个列表显得没人维护**，所以门槛设得高一些。

同时满足才建：

1. 已经有 **8 条以上**候选条目，且都放不进现有分类
2. 能被一句话说清「收什么」（能写进 `desc` 字段）
3. 有明确的读者场景——不是「技术上存在这一类」

流程：

1. 提 [新增分类 issue](https://github.com/6June6/awesome-bidding/issues/new?template=suggest-category.yml)，列出候选条目
2. 维护者在 issue 里给出结论（同意 / 合并到现有分类 / 观察）
3. 同意后，同一个人或维护者改 `data/categories.yml` 加一项，跑 `npm run build`

`categories.yml` 里新增一项要填：

```yaml
- slug: new-cat        # 小写字母数字连字符，决定 docs/list/<slug>.md 文件名
  name: 中文名
  en: English Name
  order: 130           # 最后一位往后排
  desc: 一句话说明这个分类收什么。
  needs_help: true     # 条目少时标上，README 会提示「待补充」
```

新建的分类如果少于 8 条，**请先不要建**，把候选条目暂放最接近的现有分类，在 `notes` 里标注。攒够了再拆。

## 合并与废弃

- **合并**：两个分类长期都少于 5 条且内容重叠 → 合并，条目的 `category` 批量改，`docs/list/` 下旧文件删除。
- **拆分**：单个分类超过 40 条且内部明显分成两块 → 拆，流程同「新增分类」。
- **改名**：只改 `name`，**不要改 `slug`**——slug 决定 id 与文件路径，改了会破坏外部链接。

以上都需要走 issue 讨论，不要直接提 PR。
